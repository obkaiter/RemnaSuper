# Руководство для агентов разработки

## Назначение проекта

RemnaSuper — интерактивная Bash-утилита для администрирования RemnaNode на Linux. Она устанавливается в `/opt/RemnaSuper`, запускается от root через команду `rs` и управляет Docker Compose, логами, сертификатами, geofiles, fail2ban, ss-zapret2 и диагностическими командами.

Целевая среда — Debian/Ubuntu-подобный сервер с Bash и GNU-утилитами. Часть функций требует Docker с Compose plugin, `apt`/`apt-get`, systemd, cron и уже установленный RemnaNode. Не считать macOS, Windows или POSIX `sh` поддерживаемыми средами исполнения.

## Карта репозитория

- `RemnaSuper` — точка входа. Определяет `APP_DIR`, подключает модули в фиксированном порядке, проверяет root, показывает заставку, проверяет обновления и открывает главное меню.
- `install.sh` — bootstrap-установщик из GitHub в `/opt/RemnaSuper` и создание `/usr/local/bin/rs`.
- `VERSION` — версия, используемая механизмом автообновления.
- `lib/config.sh` — общие пути, имя/версия приложения и URL внешних репозиториев.
- `lib/ui.sh` — цвета и единый набор функций вывода, меню, подтверждения и паузы.
- `lib/common.sh` — проверки окружения и общие операции с Docker Compose.
- `lib/update.sh` — проверка версии, загрузка архива и замена установленной копии.
- `lib/logs.sh`, `lib/system.sh`, `lib/geofiles.sh`, `lib/menu.sh` — загрузчики тематических модулей.
- `lib/logs/` — настройка и очистка логов и logrotate.
- `lib/system/` — сервисы, provisioning, диагностика, сертификаты и ss-zapret2.
- `lib/geofiles/` — безопасная загрузка geofiles, cron и изменение volumes RemnaNode.
- `lib/menu/` — отображение меню, предупреждения и привязка пунктов к действиям.
- `icons/` — графические материалы; текущие установщик и updater их не разворачивают.

## Архитектура и зависимости модулей

Все файлы `lib/` подключаются через `source` и работают в одном процессе и общем пространстве имён. Порядок в `RemnaSuper` значим:

1. `config.sh`
2. `ui.sh`
3. `common.sh`
4. `update.sh`
5. `logs.sh`
6. `system.sh`
7. `geofiles.sh`
8. `menu.sh`

Не запускайте файлы из `lib/` как самостоятельные программы и не добавляйте в них `main`. Если создаётся новый модуль, подключите его в соответствующем тематическом загрузчике. Загрузчики вычисляют каталог через `${BASH_SOURCE[0]}`, а временную функцию `_remnasuper_load_*_modules` удаляют после загрузки; сохраняйте этот шаблон.

Размещайте код по ответственности: интерфейс и маршрутизация — в `lib/menu/`, системное действие — в `lib/system/`, общая переиспользуемая операция — в `lib/common.sh`, значения окружения — в `lib/config.sh`. Не дублируйте пути вроде `/opt/remnanode` и имена контейнеров вне конфигурации без необходимости.

## Стиль Bash

- Используйте `#!/usr/bin/env bash`; проект намеренно использует Bash-возможности (`[[ ]]`, массивы, `mapfile`, process substitution).
- Сохраняйте UTF-8 и LF. Пользовательские сообщения и документация пишутся по-русски, идентификаторы — на английском в `snake_case`, константы — в `UPPER_SNAKE_CASE`.
- Отступ — четыре пробела. Переменные раскрывайте в кавычках, кроме мест, где разделение слов или glob нужны намеренно.
- Объявляйте рабочие переменные функции через `local`, обычно в её начале. Для диагностических данных задавайте `LC_ALL=C`, если разбор зависит от формата вывода внешней команды.
- Для вывода используйте `printf` и функции `info`, `success`, `warn`, `error`, `step`, `header`, `section`; не вводите новый несогласованный формат сообщений.
- Не включайте `set -e` или `set -u` внутри sourced-модулей: это изменит поведение всего интерактивного процесса. Точка входа использует `set -o pipefail`, а установщик — `set -euo pipefail`.
- Вспомогательные функции должны возвращать ненулевой статус при ошибке. `exit` допустим в точках входа и при окончательном завершении, но обычное действие меню должно сообщить об ошибке, при необходимости вызвать `pause` и вернуть управление меню.
- Проверяйте внешние команды через `check_command`; Docker — через `check_docker`. Не скрывайте значимую ошибку конструкцией `|| true`; она уместна только для необязательной диагностики, cleanup или best-effort rollback.

## Изменение меню и пользовательских действий

Каждое потенциально изменяющее систему действие должно проходить через `run_action` или аналогичное подтверждение. Текст подтверждения — часть механизма безопасности: точно перечисляйте скачивания, изменения файлов, перезапуски, открываемые порты и риск потери доступа. Если побочные эффекты функции изменились, одновременно обновите описание пункта меню.

При добавлении пункта:

1. Реализуйте действие в подходящем модуле.
2. Подключите новый файл в загрузчике, если он появился.
3. Добавьте отображение пункта и ветку `case` в одном меню.
4. Обновите диапазон в `prompt_choice`.
5. Сохраните семантику `0`: выход в главном меню и возврат в подменю.

Не запускайте загруженный из сети код без явного предупреждения пользователю. Для загрузок задавайте тайм-ауты, проверяйте код возврата и содержимое/наличие обязательных файлов до установки.

## Безопасность системных изменений

- Считайте `/opt`, `/etc`, `/var/log`, crontab и Docker Compose данными реального сервера. Не используйте их для локальных тестов.
- Перед изменением `docker-compose.yml` вызывайте `backup_compose`. Изменения должны быть идемпотентными и ограничиваться нужным сервисом/volume; не полагайтесь на простое совпадение текста вне требуемой YAML-секции.
- Для перезаписи конфигурации используйте временный файл, проверяйте успешность преобразования и только затем делайте `mv`. Удаляйте временные файлы во всех ветках или ставьте `trap`.
- Не перезаписывайте существующие пользовательские `.env`, сертификаты и конфиги без явной необходимости. Миграции должны сохранять прежнее состояние либо выполнять rollback при неудаче.
- Валидируйте пути до рекурсивного удаления. Особенно осторожно меняйте `install.sh` и `lib/update.sh`: updater удаляет `$INSTALL_DIR/lib`, а допустимым каталогом установки должен оставаться ровно `/opt/RemnaSuper`.
- После изменения Compose-конфигурации по возможности выполняйте `docker compose config` до остановки работающих контейнеров.
- Никогда не выводите пароли или содержимое секретных `.env` в логи. Создаваемые секреты должны иметь права `0600`.

## Проверки

В репозитории пока нет автоматических тестов и CI. Минимальная проверка всех Bash-файлов выполняется в Linux-среде из корня проекта:

```bash
set -e
while IFS= read -r -d '' file; do
    case "$file" in
        RemnaSuper|*.sh) bash -n "$file" ;;
    esac
done < <(git ls-files -z)
```

Если установлен ShellCheck, дополнительно запустите:

```bash
find lib -type f -name '*.sh' -print0 \
    | xargs -0 shellcheck RemnaSuper install.sh
```

Не используйте `sudo ./RemnaSuper` как безобидный smoke-тест: при запуске выполняется проверка обновления, а пункты меню изменяют систему. Для ручного теста точки входа обязательно задавайте `REMNASUPER_SKIP_UPDATE=1` и работайте только на одноразовой Debian/Ubuntu VM, предназначенной для интеграционных проверок.

Изменения функций, которые редактируют Compose, cron или конфиги, сначала проверяйте на фикстурах во временном каталоге, переопределив соответствующие глобальные пути после подключения модулей. Затем проверяйте идемпотентность повторным вызовом. Полный сценарий с Docker и RemnaNode выполняйте только на тестовом сервере и проверяйте как успешный путь, так и восстановление после ошибки.

## Версия, установка и документация

Автообновление сравнивает корневой `VERSION` с версией на GitHub через `sort -V`. Если изменение готовится к публикации и должно попасть на уже установленные серверы, увеличьте `VERSION`; без этого клиенты не загрузят новый код. Не меняйте версию для незавершённой локальной работы без задачи на релиз.

При изменении состава устанавливаемых файлов синхронно обновляйте и `install.sh`, и `lib/update.sh`. Сейчас оба пути установки обязаны переносить `RemnaSuper`, `VERSION` и весь `lib/`; `README.md` и `install.sh` копируются при наличии. Если runtime начнёт зависеть от нового корневого каталога или файла, добавьте его в оба механизма и в проверку содержимого архива.

Обновляйте `README.md`, если меняются команда установки, способ запуска, пользовательские возможности, переменные окружения или поведение автообновления.

## Критерии готовности изменения

- Изменение находится в правильном модуле, а новый файл подключён загрузчиком.
- Пользовательский текст соответствует реальным побочным эффектам и остаётся понятным на русском языке.
- Ошибки внешних команд обрабатываются, временные файлы очищаются, существующие настройки сохраняются.
- Повторный запуск изменяющего действия безопасен или явно блокируется с понятным сообщением.
- `bash -n` проходит для всех отслеживаемых Bash-файлов; ShellCheck выполнен, если доступен.
- Опасные интеграционные сценарии проверены только в изолированной Linux-среде.
- При подготовке релиза обновлены `VERSION` и затронутая документация.
